# ЛР2 — Требования к модулю «Сервис задач»

## 1. Назначение и границы ответственности

### 1.1. Назначение

«Сервис задач» — учебный модуль для студента, который предоставляет операции над задачами и сохраняет их состояние в JSON-файл.
Модуль должен позволять:
- создавать задачи;
- просматривать список задач;
- получать задачу по идентификатору;
- изменять название и описание задачи;
- изменять статус задачи;
- фильтровать задачи по статусу;
- искать задачи по ключевому слову;
- загружать сохранённые задачи из JSON-файла;
- сохранять актуальное состояние задач в JSON-файл.

### 1.2. Что входит в границы модуля
Модуль отвечает за:
- хранение задач в памяти во время работы;
- валидацию входных данных;
- назначение и проверку идентификаторов;
- изменение данных и статусов задач;
- чтение и запись JSON-файла;
- выдачу управляемых ошибок при некорректных данных и проблемах хранения.

### 1.3. Что не входит в границы модуля
Модуль не отвечает за:
- графический или веб-интерфейс;
- регистрацию и аутентификацию пользователей;
- авторизацию и разграничение прав доступа;
- сетевое взаимодействие;
- синхронизацию данных между несколькими устройствами;
- уведомления;
- совместное редактирование задач несколькими пользователями.

## 2. Вопросы аналитика и принятые решения

### 2.1. Сколько задач может быть у пользователя?

**Решение:** один пользователь может иметь не более 10 000 задач. При попытке создать 10 001-ю задачу модуль возвращает управляемую ошибку и не изменяет набор задач.

### 2.2. Какие статусы у задачи допустимы?

**Решение:** поддерживаются только три статуса:
- `new` — новая;
- `in_progress` — в работе;
- `done` — выполнена.

Любое другое значение недопустимо.

### 2.3. Можно ли менять текст задачи после создания?

**Решение:** да. Название и описание существующей задачи можно изменить по её идентификатору. Идентификатор при этом не меняется.

### 2.4. Как определяется уникальность задачи?

**Решение:** уникальность определяется идентификатором. Названия не обязаны быть уникальными, поэтому две задачи могут иметь одинаковое название при разных идентификаторах.

### 2.5. Что делать, если JSON-файл отсутствует?

**Решение:** отсутствие файла считается пустым хранилищем. При запуске модуль загружает пустой список без ошибки. Файл создаётся при первом успешном сохранении.

### 2.6. Что делать, если JSON-файл повреждён?

**Решение:** модуль возвращает управляемую ошибку `DataFileCorrupted` и не считает содержимое файла корректно загруженным. Повреждённый файл автоматически не перезаписывается.

### 2.7. Что считается успешным сохранением?

**Решение:** сохранение считается успешным только после завершения записи JSON без ошибки. После успешного сохранения файл должен содержать актуальное состояние задач.

### 2.8. Нужно ли учитывать регистр при поиске?

**Решение:** поиск регистронезависимый. Например, запросы `учёба`, `Учёба` и `УЧЁБА` должны давать одинаковый набор результатов.

### 2.9. По каким полям выполняется поиск?

**Решение:** поиск выполняется по названию и описанию задачи. Совпадение есть, если ключевое слово встречается хотя бы в одном из этих полей.

### 2.10. Что делать, если поиск ничего не нашёл?

**Решение:** модуль возвращает пустой список. Это штатный результат, а не ошибка.

### 2.11. Какие поля обязательны при создании?

**Решение:** название обязательно и не может быть пустым или состоять только из пробелов. Описание необязательно; при отсутствии оно принимается за пустую строку.

### 2.12. Какой статус получает новая задача?

**Решение:** при создании автоматически устанавливается статус `new`.

## 3. Функциональные требования

| ID | Требование | Проверяемость |
| FR-01 | Модуль должен позволять создать задачу с названием и описанием. | Создать задачу и проверить совпадение переданных полей. |
| FR-02 | Модуль должен назначать каждой новой задаче непустой уникальный идентификатор. | Создать несколько задач и проверить наличие и уникальность ID. |
| FR-03 | При создании задачи модуль должен устанавливать статус `new`. | Создать задачу и проверить её статус. |
| FR-04 | Модуль должен позволять получить задачу по идентификатору. | Передать существующий ID и получить соответствующую задачу. |
| FR-05 | Модуль должен возвращать список всех существующих задач. | Создать несколько задач и сравнить состав списка. |
| FR-06 | Модуль должен позволять изменить название существующей задачи. | Изменить название и получить задачу повторно. |
| FR-07 | Модуль должен позволять изменить описание существующей задачи. | Изменить описание и проверить новое значение. |
| FR-08 | Модуль должен позволять изменить статус существующей задачи только на `new`, `in_progress` или `done`. | Установить допустимый статус и проверить изменение. |
| FR-09 | Модуль должен возвращать задачи с фильтрацией по статусу. | Создать задачи с разными статусами и проверить, что фильтр возвращает только выбранный статус. |
| FR-10 | Модуль должен выполнять поиск по ключевому слову в названии и описании. | Создать задачи с известными словами и проверить результаты поиска. |
| FR-11 | Поиск должен быть регистронезависимым. | Выполнить поиск одного слова в разных регистрах и сравнить результаты. |
| FR-12 | При отсутствии совпадений поиск должен возвращать пустой список без ошибки. | Выполнить поиск отсутствующего слова. |
| FR-13 | Модуль должен сохранять актуальный набор задач в JSON-файл. | Сохранить данные и проверить наличие актуальных данных в файле. |
| FR-14 | Модуль должен загружать задачи из JSON-файла при запуске или инициализации хранилища. | Подготовить файл, загрузить модуль и проверить восстановленные задачи. |
| FR-15 | При отсутствии JSON-файла модуль должен использовать пустой набор задач без аварийного завершения. | Запустить модуль без файла и проверить пустой список. |
| FR-16 | Модуль должен ограничивать количество задач значением 10 000. | Создать 10 000 задач и проверить успешность; попытку создания 10 001-й проверить как ошибочную. |
| FR-17 | Модуль должен сохранять идентификатор задачи неизменным при изменении её названия, описания или статуса. | Изменить данные и сравнить ID до и после. |
| FR-18 | Модуль должен поддерживать повторное сохранение после изменения задачи. | Изменить задачу, сохранить, загрузить файл и проверить изменённые данные. |

## 4. Требования к данным и JSON-хранилищу

### 4.1. Расположение файла

Путь к JSON-файлу должен передаваться модулю как параметр хранилища. Конкретный путь по умолчанию может задаваться проектом, но формат файла не должен зависеть от расположения.

### 4.2. Обязательные поля задачи

Каждая задача должна содержать:
- `id` — строка, непустая;
- `title` — строка, непустая после удаления начальных и конечных пробелов;
- `description` — строка, может быть пустой;
- `status` — строка со значением `new`, `in_progress` или `done`.

### 4.3. Структура JSON

Корневой объект должен содержать ключ `tasks`, значением которого является массив объектов задач.

Эталон минимальной записи:

```json
{
  "tasks": [
    {
      "id": "1",
      "title": "Подготовить лабораторную",
      "description": "Оформить требования и сценарии",
      "status": "new"
    }
  ]
}
```

### 4.4. Правила хранения

1. Все задачи должны находиться внутри массива `tasks`.
2. У каждой задачи должны присутствовать все четыре обязательных поля.
3. Значения `id`, `title`, `description` и `status` должны иметь тип `string`.
4. `id` должен быть уникальным внутри файла.
5. `status` должен иметь только допустимое значение.
6. После успешного сохранения JSON должен быть читаемым стандартным JSON-парсером.
7. Пустое хранилище должно представляться как:
   ```json
   {
     "tasks": []
   }
   ```

## 5. Требования к ошибкам и сообщениям

Ошибки должны быть управляемыми: модуль не должен завершаться аварийно из-за ожидаемой ошибки входных данных или хранилища.

| Код ошибки | Ситуация | Ожидаемое поведение |
|---|---|---|
| `EmptyTitle` | Название пустое или состоит только из пробелов | Создание/изменение не выполняется; возвращается понятная ошибка. |
| `InvalidStatus` | Передан статус вне списка `new`, `in_progress`, `done` | Изменение не выполняется; возвращается понятная ошибка. |
| `TaskNotFound` | Указанный ID отсутствует | Операция над задачей не выполняется; возвращается понятная ошибка. |
| `TaskLimitExceeded` | Превышен лимит 10 000 задач | Новая задача не создаётся; возвращается понятная ошибка. |
| `DataFileCorrupted` | JSON синтаксически некорректен или имеет несовместимую структуру | Загрузка не считается успешной; возвращается понятная ошибка. |
| `DataFileReadError` | Файл существует, но не может быть прочитан | Загрузка не считается успешной; возвращается понятная ошибка. |
| `DataFileWriteError` | Не удалось записать файл | Сохранение считается неуспешным; возвращается понятная ошибка. |

Сообщение ошибки должно позволять определить причину без анализа внутреннего кода модуля.

## 6. Ограничения и допущения

1. В рамках лабораторной предполагается один логический пользователь.
2. Предел количества задач — 10 000.
3. Уникальность обеспечивается только идентификатором.
4. Названия задач могут повторяться.
5. Статус новой задачи всегда `new`.
6. Поиск выполняется без учёта регистра.
7. Поиск проверяет название и описание.
8. Пустой результат поиска не считается ошибкой.
9. Отсутствующий файл считается пустым хранилищем.
10. Повреждённый файл не должен автоматически перезаписываться.
11. Модуль работает с локальным JSON-файлом; база данных не используется.
12. Интерфейс пользователя не является частью лабораторной.
13. Сетевая синхронизация и многопользовательский режим не рассматриваются.

## 7. Критерии приёмки

- **AC-01. Создание:** после создания корректной задачи она получает непустой уникальный ID, статус `new`, появляется в списке и может быть сохранена в JSON.
- **AC-02. Загрузка:** после сохранения и последующей загрузки задачи восстанавливаются с теми же ID, названиями, описаниями и статусами.
- **AC-03. Изменение статуса:** существующей задаче можно установить только допустимый статус; недопустимый статус не изменяет данные.
- **AC-04. Поиск:** поиск находит задачи по названию или описанию независимо от регистра; при отсутствии совпадений возвращается пустой список.
- **AC-05. Ошибки:** пустое название, неизвестный ID, недопустимый статус и превышение лимита приводят к управляемым ошибкам без нежелательного изменения данных.
- **AC-06. Хранилище:** отсутствие файла приводит к пустому набору задач, а повреждённый JSON приводит к управляемой ошибке `DataFileCorrupted` без автоматической перезаписи исходного файла.

## 8. Самопроверка требований

- Каждое требование имеет наблюдаемое ожидаемое поведение и способ проверки.
- Не используются неопределённые характеристики вроде «удобно», «быстро», «красиво» или «надёжно» без измеримых условий.
- Требования разделены по одной основной мысли.
- Описаны штатные, альтернативные и ошибочные ситуации.
- Определены границы ответственности модуля.
- Формат JSON зафиксирован примером и правилами типов.
