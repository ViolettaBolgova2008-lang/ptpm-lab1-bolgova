### 2. Краткое описание проблемы

Для анализа выбран дефект **BUG-01: «Невозможно создать задачу»**, ранее оформленный в GitHub Issues.

Проблема относится к основному пользовательскому сценарию создания задачи. Пользователь выполняет предусмотренные действия для добавления новой задачи, однако ожидаемое создание задачи не происходит. Данный дефект выбран для лабораторной работы №7, поскольку его можно исследовать через повторное выполнение одного и того же сценария и сузить область поиска до логики создания задачи.

### 3. Нарушенное требование и сценарий

**Связь с лабораторной работой №6:** BUG-01, Issue #10.

Затронут пользовательский сценарий создания новой задачи.

**Ожидаемое поведение:** после корректного ввода необходимых данных система должна создать новую задачу, присвоить ей необходимые поля и отобразить подтверждение успешного создания. При повторном просмотре списка созданная задача должна присутствовать в данных приложения.

**Фактическая проблема:** сценарий создания задачи завершается некорректно — новая задача не создаётся ожидаемым образом.

> Примечание: идентификаторы требований и тест-кейсов следует сверить с файлами предыдущих лабораторных работ, если в них используются конкретные обозначения R-__, S-__ или TC-__.

4. Ввести корректное название задачи.
5. Ввести остальные обязательные данные задачи.
6. Подтвердить создание задачи.
7. Перейти к просмотру списка задач.
8. Проверить наличие только что созданной задачи.

### 7. Фактический результат

При выполнении сценария создания задачи ожидаемая новая задача не появляется в системе/списке задач. Таким образом, основной сценарий создания задачи не завершается ожидаемым результатом.

**Симптом:** пользователь не получает корректно созданную задачу после подтверждения ввода.

### 8. Ожидаемый результат

После подтверждения корректно заполненной формы система должна:

- создать новую задачу;
- сохранить введённые данные;
- присвоить задаче необходимые служебные поля;
- сообщить пользователю об успешном создании;
- отобразить созданную задачу при последующем просмотре списка.

### 9. Проверка воспроизводимости

Для лабораторной работы дефект необходимо проверить повторно в одинаковом окружении.

**Результат проверки:**

- Попытка №1: воспроизвести по шагам выше.
- Попытка №2: повторить тот же сценарий.
- Попытка №3: повторить сценарий ещё раз.

**Вывод:** дефект считается стабильно воспроизводимым, если одинаковый сценарий приводит к одинаковому неправильному результату при каждом повторе.

> Перед сдачей необходимо фактически выполнить эти три проверки и при необходимости скорректировать формулировку результата. В документе не следует выдавать предположение за наблюдение.

### 10. Локализация дефекта

По характеру проявления дефекта проблема относится к **логике создания и сохранения задачи**.

Область поиска можно сузить следующим образом:

1. **Интерфейс/команда создания** — проверить, действительно ли введённые данные передаются дальше после подтверждения.
2. **Логика создания объекта задачи** — проверить формирование нового объекта и присвоение его полей.
3. **Сохранение задачи** — проверить, добавляется ли созданный объект в коллекцию задач.
4. **Хранение данных** — проверить, передаётся ли обновлённый набор задач в механизм сохранения.
5. **Отображение списка** — проверить, не создаётся ли задача корректно, но затем не теряется ли при получении списка.

Таким образом, первоначальную область поиска следует сосредоточить на цепочке:

`ввод данных → создание задачи → добавление в коллекцию → сохранение → получение списка`.

### 11. Предполагаемая причина

Предполагаемая причина на данном этапе является **гипотезой**, а не окончательно доказанной причиной.

Наиболее вероятно, что ошибка находится в одном из следующих логических участков:

- функция обработки команды создания задачи;
- функция формирования объекта задачи;
- добавление нового объекта в коллекцию;
- вызов сохранения обновлённых данных.

Для окончательного определения причины необходимо проследить выполнение сценария от момента подтверждения ввода до момента появления задачи в списке.

### 12. Симптом, локализация и предполагаемая причина

| Локализация | Логика создания задачи и последующей передачи данных на сохранение |

### 15. Почему нельзя исправлять дефект без локализации

Если разработчик начнёт исправлять проблему без понимания условий её возникновения и места локализации, он может изменить участок кода, который не является причиной дефекта. Это может устранить только внешний симптом или создать новые ошибки в связанных сценариях. Без воспроизводимых шагов также невозможно надёжно сравнить поведение до и после исправления. Поэтому сначала необходимо воспроизвести дефект, определить область поиска причины и только после этого переходить к исправлению и ретесту.
