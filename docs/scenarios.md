# ЛР2 — Пользовательские сценарии «Сервис задач»

## 1. Роли

### Пользователь

Студент, который создаёт и изменяет свои задачи, просматривает список и выполняет поиск.

### Система

Модуль «Сервис задач», который принимает операции пользователя, валидирует данные, хранит задачи и работает с JSON-файлом.
## 2. Сценарии

### SC-01. Создание задачи

**Приоритет:** критический

**Цель:** создать новую задачу.

**Условия:** модуль запущен; количество существующих задач меньше 10 000; хранилище доступно.

**Шаги:**
1. Пользователь вводит название «Подготовить лабораторную».
2. Пользователь вводит описание «Оформить требования и сценарии».
3. Пользователь подтверждает создание.
4. Система проверяет название.
5. Система создаёт задачу.

**Результат:** задача получает уникальный непустой ID, статус `new`, появляется в списке и сохраняется в JSON при успешном сохранении.

---

### SC-02. Просмотр списка задач

**Приоритет:** критический

**Цель:** увидеть существующие задачи.

**Условия:** в хранилище есть несколько задач.

**Шаги:**
1. Пользователь запрашивает список задач.
2. Система загружает актуальный набор задач.
3. Система возвращает список.

**Результат:** пользователь получает все существующие задачи с ID, названием, описанием и статусом.

### SC-03. Изменение статуса

**Приоритет:** критический

**Цель:** отметить задачу как выполняемую или завершённую.

**Условия:** задача с выбранным ID существует.

**Шаги:**
1. Пользователь выбирает задачу.
2. Пользователь устанавливает статус `in_progress`.
3. Система проверяет допустимость статуса.
4. Система изменяет статус.
5. Система сохраняет актуальные данные.

**Результат:** статус задачи становится `in_progress`, ID и остальные поля сохраняются.



### SC-04. Поиск по ключевому слову

**Приоритет:** важный

**Цель:** найти задачи по известному слову.

**Условия:** существуют задачи, в названии или описании которых встречается искомое слово.

**Шаги:**
1. Пользователь вводит ключевое слово.
2. Система ищет его в названии и описании.
3. Система не учитывает регистр букв.
4. Система возвращает найденные задачи.

**Результат:** возвращаются только задачи, содержащие ключевое слово в названии или описании.

### SC-05. Загрузка задач из файла при старте

**Приоритет:** критический

**Цель:** продолжить работу с ранее сохранёнными задачами.

**Условия:** существует корректный JSON-файл с задачами.

**Шаги:**
1. Пользователь запускает или инициализирует модуль.
2. Система читает JSON-файл.
3. Система проверяет структуру данных.
4. Система загружает задачи.

**Результат:** список содержит те же задачи, ID, названия, описания и статусы, которые были сохранены ранее.

### SC-06. Отсутствие файла данных

**Приоритет:** важный

**Цель:** начать работу без ранее созданного файла.

**Условия:** JSON-файл отсутствует.

**Шаги:**
1. Пользователь запускает модуль.
2. Система проверяет наличие файла.
3. Система обнаруживает, что файл отсутствует.
4. Система инициализирует пустой набор задач.
5. Пользователь запрашивает список.

**Результат:** модуль не завершается с ошибкой, список задач пуст. При создании и последующем сохранении задача записывается в новый JSON-файл.

### SC-07. Повреждённый JSON-файл

**Приоритет:** важный

**Цель:** корректно обработать невозможность загрузить данные.

**Условия:** JSON-файл существует, но содержит некорректный JSON или несовместимую структуру.

**Шаги:**
1. Пользователь запускает модуль.
2. Система пытается прочитать файл.
3. Система обнаруживает ошибку формата.
4. Система возвращает `DataFileCorrupted`.

**Результат:** загрузка не считается успешной; пользователь получает понятное сообщение об ошибке; исходный повреждённый файл не перезаписывается автоматически.

### SC-08. Попытка установить недопустимый статус

**Приоритет:** важный

**Цель:** проверить защиту задачи от некорректного статуса.

**Условия:** существует задача с выбранным ID.

**Шаги:**
1. Пользователь выбирает задачу.
2. Пользователь передаёт статус `cancelled`.
3. Система проверяет допустимые значения.
4. Система отклоняет операцию.

**Результат:** возвращается ошибка `InvalidStatus`; исходный статус задачи не изменяется.

### SC-09. Создание задачи с пустым названием

**Приоритет:** важный

**Цель:** предотвратить создание некорректной задачи.

**Условия:** модуль работает, лимит задач не достигнут.

**Шаги:**
1. Пользователь оставляет название пустым или вводит только пробелы.
2. Пользователь подтверждает создание.
3. Система выполняет валидацию.
4. Система отклоняет создание.

**Результат:** возвращается ошибка `EmptyTitle`; новая задача не появляется в списке и не записывается в JSON.

### SC-10. Изменение названия и описания задачи

**Приоритет:** важный

**Цель:** актуализировать текст существующей задачи.

**Условия:** задача существует.

**Шаги:**
1. Пользователь выбирает задачу по ID.
2. Пользователь вводит новое название.
3. Пользователь вводит новое описание.
4. Система проверяет название.
5. Система сохраняет изменения.

**Результат:** название и описание обновлены, ID и статус остались прежними.

### SC-11. Поиск без совпадений

**Приоритет:** дополнительный

**Цель:** проверить штатную обработку пустого результата поиска.

**Условия:** в задачах нет указанного ключевого слова.

**Шаги:**
1. Пользователь вводит слово, которого нет в названиях и описаниях.
2. Система выполняет поиск.
3. Система не находит совпадений.

**Результат:** система возвращает пустой список без ошибки.

### SC-12. Попытка получить несуществующую задачу

**Приоритет:** важный

**Цель:** корректно обработать неизвестный идентификатор.

**Условия:** задачи с указанным ID не существует.

**Шаги:**
1. Пользователь передаёт ID, отсутствующий в списке.
2. Система выполняет поиск задачи.
3. Система не находит задачу.

**Результат:** возвращается ошибка `TaskNotFound`; данные существующих задач не изменяются.

### SC-13. Достижение лимита задач

**Приоритет:** дополнительный

**Цель:** проверить граничное ограничение количества задач.

**Условия:** у пользователя уже есть 10 000 задач.

**Шаги:**
1. Пользователь пытается создать ещё одну задачу.
2. Система проверяет количество задач.
3. Система обнаруживает превышение лимита.

**Результат:** возвращается ошибка `TaskLimitExceeded`; количество задач остаётся равным 10 000.

## 4. Альтернативные и ошибочные сценарии

К альтернативным и ошибочным относятся:
- SC-06 — файл отсутствует;
- SC-07 — JSON повреждён;
- SC-08 — недопустимый статус;
- SC-09 — пустое название;
- SC-11 — поиск без совпадений;
- SC-12 — неизвестный ID;
- SC-13 — превышение лимита.

Таким образом, набор содержит более трёх сценариев, проверяющих нестандартное поведение.

## 6. Проверяемость

### Сценарий SC-01 — создание задачи

**Вопрос тестировщика 1:** что произойдёт, если название задачи пустое или состоит только из пробелов?

**Ожидаемая проверка:** система должна вернуть `EmptyTitle`, не создать задачу и не изменить JSON-хранилище.

**Вопрос тестировщика 2:** как понять, что сохранение действительно прошло успешно?

**Ожидаемая проверка:** после успешного сохранения задача должна присутствовать в JSON-файле, а после повторной загрузки — иметь тот же ID, статус, название и описание.

### Сценарий SC-07 — повреждённый JSON-файл

**Вопрос тестировщика 1:** что произойдёт, если файл содержит некорректный JSON?

**Ожидаемая проверка:** система должна вернуть `DataFileCorrupted`, не считать загрузку успешной и не завершиться аварийно.

**Вопрос тестировщика 2:** что произойдёт с исходным повреждённым файлом?

**Ожидаемая проверка:** система не должна автоматически перезаписывать повреждённый файл при попытке загрузки.
